# gdd system alignment

## Goal

梳理当前 GDD / 提案中的核心玩法系统，区分“已经落地或有明确工程基线”的内容与“仍停留在设想、未来扩展或需要改写”的内容，并在用户协助下逐项调整未落地系统的表述或范围。

## What I Already Know

* 用户正在撰写项目提案，当前关注“核心玩法机制”章节。
* 提案希望从玩家视角按子系统介绍机制，而不是按回合流程展开。
* 当前用户认同先按六块组织：国策与部长、资源与产能、科技与制度、城市建筑扩张、军事冲突、情报与亲政。
* 项目文档中存在不少尚未实际落地的系统，需要避免在提案中写成已经完成的玩法。
* 当前仓库文档显示：资源/点数/科技/建筑/配方/基础战争闭环已有较明确工程基线；复杂部长执行、信息失真、完整物流、制度完整 UI、外交等仍可能属于未来或未收口内容。

## Assumptions

* 本任务先以文档和设计口径对齐为主，必要时再进入代码修改。
* 需要优先检查 `docs/gdd/2026-04-15-panoptes-gdd-v1-detailed.md`、`docs/gdd/2026-04-15-panoptes-gdd-v1-structured.md`、README 和当前实现计划文档。
* 未落地系统不一定全部删除，可能改成“设计目标”“后续扩展”“当前版本预留接口”等更准确表述。

## Open Questions

* 第一轮要优先收口哪一个系统：部长与情报、资源与物流、制度、还是军事扩展？

## Requirements

* 输出一份按系统划分的落地状态审查结果。
* 对每个系统标注：当前可写为已实现/基线、当前应写为受限版本、当前应写为未来扩展。
* 与用户逐项确认需要改写的未落地系统。
* 修改后的提案口径必须避免承诺当前版本还没有的玩法。

## Acceptance Criteria

* [ ] 已完成六个系统的落地状态初筛。
* [ ] 至少完成用户指定的第一组未落地系统改写。
* [ ] 改写后的内容能直接进入提案或 GDD。
* [ ] 若涉及代码层改动，补充对应实现与验证步骤。

## Definition Of Done

* 文档修改完成并通过人工审阅。
* 如有代码修改，运行相关测试或说明无法运行的原因。
* 若发现新的长期约束，更新 Trellis spec 或任务记录。

## Out Of Scope

* 不一次性重写完整 GDD。
* 不把未来部长 AI、完整物流、外交等大系统在当前轮次内强行实现。
* 不改变 proto、静态数据或生成代码，除非后续用户明确要求进入实现。

## Technical Notes

* 必须遵守 `AGENTS.md`：禁止手改生成代码，客户端不做游戏逻辑，游戏数值来自根 `data/` 作者源。
* Trellis 当前识别为单仓库项目，spec layers: backend, frontend。
* 若进入实现，应按 Trellis Phase 2 走实现与检查流程。
